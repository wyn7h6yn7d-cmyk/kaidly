## 1. Executive summary

The audit found **no Critical, High or Medium findings**. Tenant isolation, role checks,
commercial-access enforcement, Platform Admin separation, log immutability and file access
are enforced in the database (RLS, column grants, definer functions with explicit checks,
storage policies) and held under direct API attack. Two **Low** hardening issues were fixed
(CSV cells starting with a line break were not neutralised; error logs could contain an
invitation token from the request path). The remaining items are informational or accepted
pre-launch risks (§36). A new raw-API security suite (`e2e/security-api.spec.ts`, 12 tests)
now guards these properties in CI; it was mutation-tested.

Within the tested scope, no unresolved Critical or High security findings remain. This is
not proof of absence of vulnerabilities (§40).

## 2. Scope

In scope: the Next.js 16 application (pages, Server Actions, route handlers, proxy,
instrumentation, client storage), the Supabase database (all migrations: tables, RLS, grants,
functions, triggers, views, cron), Storage (`documents` bucket and policies), Auth flows and
email templates, CI, build configuration and the production deployment's public surface.

Out of scope / not possible: authenticated tests against Production (no credentials
available to automation — no bypass was created), Supabase/Vercel platform internals,
denial-of-service load testing, image-codec exploit research, social engineering.

## 3. Architecture reviewed

Browser → Vercel (Next.js App Router, `proxy.ts` session refresh + sign-in gate) →
Supabase (PostgREST/RPC, Auth, Storage) with the **publishable key and the user's own
session only**. No service-role key exists in the application or its environment. Every
customer read and write is decided by Postgres: RLS policies through
`private.org_ids(min_role)` (membership, live session, not deactivated, trial/active),
column-level grants, SECURITY DEFINER RPCs with explicit checks, and Storage policies that
join `documents` under the caller's RLS. Platform administration is a separate set of
definer RPCs gated by `private.require_platform_admin()` (user-id table). Reports are built
server-side from the user's RLS reads; files are served by 60-second signed URLs after an
access-checked route.

## 4. Trust boundaries

1. Internet → Vercel edge (TLS, headers, proxy redirect for private routes).
2. Browser → Server Actions / route handlers (session cookie; every action re-resolves the
   company from the slug through RLS).
3. Browser/server → Supabase API with the user's JWT (the real security boundary: RLS,
   grants, definer checks).
4. Supabase API → `private` schema (not exposed through the API; reachable only via
   reviewed definer functions).
5. Storage objects ↔ `documents` rows (paths are generated by the database; policies match
   object names to rows the caller can see).
6. Database owner (migrations, bootstrap) — outside the application; no runtime path.

## 5. Methodology

- **Threat model** with 14 actors (anonymous visitor; viewer/operator/admin/owner;
  expired-company and deactivated-company members; multi-company member; customer probing
  admin; platform admin; disabled user; revoked session; malicious tenant; raw HTTP/RPC
  caller) against the protected assets (identities, profiles, all company data incl. history,
  files, signed access, reports, notifications, memberships, access state, admin data/audit,
  secrets, internal metadata).
- **Catalog audit** of a database built from zero (`supabase db reset`): RLS flags, every
  table/column/sequence/function/schema privilege for `anon`, `authenticated`, `PUBLIC`,
  every SECURITY DEFINER function, views, storage bucket and policies, dynamic SQL search.
- **Code audit**: inventory of all Server Actions (13 files, 52 actions), 5 route handlers,
  HTML sinks, link/redirect sources, caching, logging, browser storage, env usage, client
  bundles.
- **Adversarial tests at the API layer** with real sessions and the public key (new
  `e2e/security-api.spec.ts`), verifying outcomes in the database; existing pgTAP suites
  (680+ assertions) and E2E suites as further evidence.
- **Mutation testing** of the new suite (deliberately granting forbidden privileges → the
  suite fails) and of the fixes.
- **Production**: read-only inspection of headers, CSP, health, routing, redirects, CORS.

## 7. Sessions

`private.session_active()` (session row exists in `auth.sessions`, user not banned) is part of
`org_ids()`/`org_ids_readable()`; company creation/joining are guarded by
`a_require_live_session`. Sign-out, "sign out other devices", password change, admin session
revocation and account disable therefore remove **all company reads and writes from the next
request** (pgTAP `170_release_hardening`, E2E `account`/`admin`). Remaining until the access
token expires (≤ 1 h): the already-rendered empty frame and the user's own profile row —
no operational company data, no writes. After sign-out a protected URL answers 307 to login
(verified); browser history may still show previously painted pages (normal browser
behaviour, no live data). Unsaved drafts are cleared from the tab on sign-out (E2E).

## 8. Multi-tenancy

Two isolated tenants with every record type, plus expired, deactivated and multi-company
cases, were attacked with valid foreign UUIDs through PostgREST tables and views, RPCs, global
search (marker, wildcards, SQL-ish input), notifications, Storage (download, sign, upload,
upsert, remove), route handlers (document open, report export with foreign filters,
notification redirect), pages (foreign slug and ids) and a Server Action with a tampered
company slug. **Result: no disclosure and no mutation in every case**; denials are
indistinguishable from unknown ids (404 / empty). Slugs are routing identifiers only —
knowing one grants nothing (§54 of the brief): every lookup goes through membership.

## 9. RLS

All 12 `public` tables have RLS enabled (baseline test fails otherwise). Policy matrix
(`authenticated` only; `anon` has no table privileges anywhere in `public`):

| Table | SELECT | INSERT | UPDATE | DELETE |
|---|---|---|---|---|
| organisations | V+ of the company | via `create_organisation` | A+ (6 columns) | never (RPC, empty only) |
| organisation_members | V+ | via RPCs (create/accept) | A+ `role` only; last owner protected | A+/Ow/self per rules |
| organisation_invitations | A+ (no token hash) | `create_invitation` | revoke RPC | — |
| profiles | self + co-members | trigger | self: name, phone, locale | — |
| sites, electrical_installations | V+ | A+ | A+ (listed columns) | — |
| log_entries | V+ | Op+ (append-only; corrections are rows) | **none** | **none** |
| scheduled_activities | V+ | A+ | A+; completion via RPC | — |
| deficiencies | V+ | Op+ | Op+ (fields, open⇄in progress); resolve via RPC | **none** |
| documents | V+ ready | Op+/A+ by placement | A+ title/category/archive (general docs) | uploader, incomplete only |
| notifications | own rows | generator only | own `read_at` only | — |
| activity_history | A+ | triggers only | none | none |

Writes use `org_ids(role)` (includes trial/active and not-deactivated); admin-level reads
use `org_ids_readable`. Tested directly in pgTAP (20 files) and at the API layer.

## 10. Database grants

- `anon`: no table privileges in `public`; cannot execute any function in `public`/`private`
  (baseline test). Storage default grants exist but no anon policy → denied.
- `authenticated`: SELECT on tables/views; INSERT/UPDATE only on explicit column lists
  (mass assignment of `organisation_id` changes, `created_by`, `resolved_by`, slugs, access
  state, timestamps is refused with a privilege error — tested); no TRUNCATE/REFERENCES/
  TRIGGER; USAGE on `private` only so policies can call `org_ids`, no table privileges there;
  executes exactly the reviewed function list (baseline test pins it).
- No sequences in `public`/`private`; no CREATE on any schema for API roles.
- `private` is not exposed through the API (direct schema request refused — tested).
- New tables get no privileges by default (baseline probe).

## 11. Privileged functions (SECURITY DEFINER)

65 definer functions, **all with `search_path=''`** and schema-qualified references. The 37
callable by `authenticated` all check the caller (`require_platform_admin`, `org_ids`,
`auth.uid()` membership/role checks); trigger and helper functions are not executable by API
roles. **No dynamic SQL** (`EXECUTE`/`format`) exists in any function, so SQL and identifier
injection through RPC arguments is impossible; all list functions clamp limits
(search ≤ 25/group, notifications ≤ 100, admin lists ≤ 200–500). The search_path attack is
covered by the baseline test (every definer function pins `search_path`) — with an empty
path, attacker-created objects can never be resolved.

## 13. Platform Admin

Authorised only by `private.is_platform_admin()` (row keyed by immutable user id, `active`).
Every `admin_*` function calls `require_platform_admin()` first and answers `not_found` to
others. All 20 admin RPCs were called by a company owner and anonymously with correct
arguments (verified to reach the database): every one refused, nothing changed (role,
membership, ban, access state checked afterwards). Mutations write
`private.admin_audit_log` (actor, action, target, safe summary); users cannot read or write
the audit log (private schema). **Data minimisation:** no admin function returns log
descriptions, resolutions, notes, files or storage paths; admins have no tenant RLS access
and no Storage policy. `admin_deadlines` shows activity/deficiency **titles** and places for
platform-wide deadline tracking (explicit product requirement) — informational.
**Bootstrap:** `private.bootstrap_platform_admin(email)` is executable only by the database
owner, requires exactly one confirmed account (refuses ambiguity), audits the grant; there is
no runtime path to it. Kenneth remains the only active Production admin.

## 14. Trial / access enforcement

`private.can_company_write()` (trial or full access, from timestamps compared with `now()` —
no time-zone loophole) is inside `org_ids()` for every role above viewer. Expired and
deactivated companies were attacked with raw INSERT/UPDATE (sites, entries, corrections,
deficiencies, document registration), completion, resolution and import: **all refused, data
unchanged**; reads stay available in expired companies (reports allowed by policy), exports
of deactivated companies are 404. Members cannot change access (`organisation_access` is
private; `admin_*` refused).

## 15. Operating-log integrity

No UPDATE/DELETE grants or policies; trigger `log_entries_no_update_delete` plus a TRUNCATE
trigger refuse changes even for the owner role. Direct update/delete attempts left the entry
unchanged (API suite). Corrections must point at an original of the same installation
(composite FK) and carry a reason; a correction of another tenant's entry is refused.

## 16. Deficiency integrity

No DELETE; resolution only through `resolve_deficiency` (resolution required, final);
`status`/`resolved_*` are not directly writable (column grants; attempt refused in the API
suite); foreign, viewer and expired-company resolutions refused (pgTAP 070/150, API suite).

## 17. Notifications

User-scoped RLS; only `read_at` of one's own rows is updatable (other columns refused, other
users' rows unaffected); rows are created only by `private.generate_activity_reminders()`
for members of the activity's company (pgTAP 140), unique per (user, activity, occurrence,
threshold, channel). Links are built from database ids (slug + activity id), never stored
URLs; the redirect route ignores foreign ids and does not mark them read.

## 18. Search

`search_kaidly` is SECURITY INVOKER (caller's RLS), excludes deactivated companies, escapes
`%`/`_`/`\`, uses static SQL, clamps results. Marker, wildcard, quote and SQL-ish queries from
Tenant A returned nothing of Tenant B; no storage paths, ids of foreign companies or secrets
appear in results.

## 19. Reports / exports

Company from membership (slug → RLS), never from a client id; foreign or deactivated → 404;
filters parsed and re-applied under RLS (a foreign installation filter returns nothing of the
other tenant); generated on request, `attachment` with ASCII file names, `private, no-store`,
`nosniff`; capped at 5000 rows server-side (not request-controlled). PDFs are pdfmake text
only, with network access disabled (`setUrlAccessPolicy(() => false)`) and disk access limited
to the font directory; hostile values (HTML, script, RTL overrides, 4900-character text)
produce a valid PDF. **CSV**: cells starting with `=`, `+`, `-`, `@`, tab **or a line break**
are prefixed with `'` (line breaks were missed before — fixed, KSA-01).

## 20. Import

`import_company_data`: owner/admin of a writable company only (`org_ids('admin')`), sites
matched by name inside the company (no client ids), all rows or none, idempotent per token
(unique per company), formula values and over-long values refused, ≤ 1000 rows; batch records
private. Foreign company, operator, viewer, expired, deactivated, anonymous: refused
(pgTAP 180, 34 assertions; API suite). File parsing limits (1 MB, strict UTF-8, RFC 4180) are
client-side conveniences; the database re-validates everything.

## 21. Storage / uploads

One private bucket (`public = false`), 25 MB limit and a MIME allowlist (PDF, JPEG, PNG,
WebP, DOCX, XLSX) enforced by Storage; the `documents` row checks the same list and size.
Object paths are generated by the database (`<org>/<document>/<uuid>`); uploads only to the
caller's own registered pending path; no UPDATE policy (no overwrite/upsert); reads only for
`ready` rows visible under RLS. Tested: foreign download/sign/upload/upsert/remove refused or
without effect; public URL does not exist; SVG and HTML uploads refused by the bucket and by
the row check. Upload abuse limits (per user/company counters, failed attempts count) are
database-enforced (pgTAP 170). Photos are re-encoded to JPEG in the browser before upload;
originals of other allowed types are stored as uploaded.

## 22. Signed URLs

Created only by the access-checked route after an RLS read of a `ready` document, 60 s
lifetime, redirect with `no-store` and `Referrer-Policy: no-referrer`; `?lae=1` forces
`attachment` with the stored (sanitised) file name. A signed URL is bearer access for 60 s —
accepted by design. Files are served from the Supabase origin, never from kaidly.ee, so an
uploaded file can never run as same-origin content.

## 23. XSS / injection

One `dangerouslySetInnerHTML` (a static `<html lang>` script with no user input); no raw
HTML or markdown rendering; React escapes all user values. Stored payloads in company, site
and deficiency names were rendered as text for a member and on Platform Admin screens without
execution (API suite). All `href`s are internal paths built from ids; the only external link
is a validated `mailto:` (strict address pattern). No dynamic SQL anywhere (§11).

## 24. CSRF / CORS

Server Actions: POST with Next.js' built-in Origin/Host check; session cookies are
`SameSite=Lax`; mutations require the `Next-Action` header (forces a CORS preflight that
the deployment does not grant). Route handlers are GET-only; the only state change via GET
marks one's own notification read (requires knowing its UUID) — informational (KSA-I3).
CORS: the application sets no CORS headers; Vercel adds `Access-Control-Allow-Origin: *` to
**public prerendered/static responses only** (landing, login, legal, icons) — never with
credentials, never on authenticated or redirected responses, so no private data is
readable cross-origin (KSA-I4).

## 25. Next.js / Server Actions / API

52 Server Actions: every company-data action starts with `actionContext(formData, minRole)`
(company from slug through RLS, role and read-only checks; archive/restore via a shared
helper), account actions with `requireUser()`, admin actions with the platform-admin check;
the language actions only set a cookie and the caller's own profile row (RLS), and the guide
show/hide actions check membership and only set a browser UI cookie. Inputs are validated
with zod, referenced records are re-read inside the company, and only error codes are
returned. The
database repeats every check. A tampered company slug in a real form submission created
nothing (API suite). Route handlers: `/api/health` (status only), `/auth/confirm`
(allowlisted), document open, report export, notification redirect — all reviewed (§19, §22,
§17).

## 26. Cache isolation

No `use cache`, `unstable_cache` or route `revalidate` for tenant data; React `cache()` is
per request. Authenticated routes are partial prerenders whose static shell is built without
cookies — any session read suspends into the per-request stream. The built shells were
searched for tenant names, emails, ids, storage paths and tokens: none. Signed-out requests
to private routes are redirected by the proxy before any shell is served; dynamic responses
are `no-cache, must-revalidate`, exports and file redirects `private, no-store`.

## 27. Error / logging leakage

UI and APIs return application error codes only (no SQL, stack, schema or provider text);
error pages show a digest. Server logs: one JSON line per error with route, method, digest
and a truncated message; no headers, cookies, bodies or query strings. **Fixed (KSA-02):**
the logged path is now passed through `safeLogPath`, which drops query/fragment and redacts
`/invite/<token>`. The proxy logs only configuration error messages (no request data).

## 28. Secrets

Tracked files and the full git history were scanned for service-role/JWT keys, `sb_secret_`,
Supabase access tokens, Vercel/GitHub/AWS tokens, private keys, database URLs with
passwords and signed URLs: **none found**. `.env*` files are ignored; `.env.example` holds
placeholders. Client bundles contain only the public Supabase URL and supabase-js library
code — no service-role key, database URL, contact or admin email; no public source maps.
The only fixed password in the repository is the fictional local-seed/QA password (local
stack only).

## 32. Availability / abuse controls

Bounded: search per group, notification/admin list limits, report rows (5000), import
(1000 rows, 1 MB in the browser; Server Action bodies 1 MB by default), upload counters and
size limits, auth rate limits (Supabase). Not bounded: number of companies a user can create
(each starts a trial) — business-logic note, no security impact (KSA-I6). No load testing
was performed against Production.

## 33. Backup / resilience note

Separate from application security: Production has **no restorable database backups**
(PITR off) and Storage files are not covered by database backups. This is a data-loss /
resilience risk, not a confidentiality or authorisation vulnerability. Do not add real
customer data until resolved (RELEASE_CHECKLIST.md).

*Update 2026-10-07:* manual Production database + Storage backups now exist (tooling, local
restore rehearsal, real backups taken — BACKUP_RECOVERY.md); Supabase-side daily backups/PITR
remain off (owner decision).

## 35. Fixed findings

- **KSA-01** — `toCsv` now neutralises `=`, `+`, `-`, `@`, tab and line breaks at the start of
  a cell. Regression: unit test with 8 payloads (mutation-checked: reverting the fix fails
  it) and an E2E export test with hostile log entries.
- **KSA-02** — `safeLogPath()` (`lib/log-path.ts`) used by the error logger: no query or
  fragment, `/invite/<token>` → `/invite/[token]`. Regression: unit test.

## 36. Remaining risks

KSA-03 (manual, with SMTP), the informational items above, the inherent 60-second bearer
nature of signed URLs and ≤ 1 h validity of an access token's empty frame after revocation,
Supabase/Vercel platform trust, and the non-security pre-launch items (backups, Storage
recovery, SMTP, legal operator facts).

- Paste the reviewed email templates; configure SMTP with SPF/DKIM/DMARC.
- Optional: Vercel Deployment Protection stays on for Previews; keep the Protection Bypass

## 40. Overall conclusion

Within the tested scope — the full database catalog, every Server Action and route handler,
two-tenant adversarial tests at the API layer, Storage, reports, import, search,
notifications, sessions, caching, headers, secrets and dependencies — **no unresolved
Critical or High security findings were identified**, and no Medium findings. Two Low issues
were fixed; one Low issue (KSA-03) awaits SMTP. This does not prove the absence of
vulnerabilities: authenticated Production behaviour, the Supabase/Vercel platforms and
load-based attacks were outside what could be tested here.
